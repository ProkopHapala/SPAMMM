## Analysis: Why Brute-Force Can Win for Small Molecules

### Current two-stage pipeline cost

```
Stage 1 (grid build):  N_grid × N_atoms pair evals  +  write N_grid × 16 bytes to global
Stage 2 (relax):       N_scan × N_z × N_relax × 1 texture read
```

Typical numbers (100³ grid, 50×50 scan, 60 z-slices, ~50 relax steps, 64 atoms):
- Stage 1: 1M × 64 = **64M pair evals** + 16 MB global write
- Stage 2: 2500 × 60 × 50 = **7.5M texture reads** (cheap, cached)

### Brute-force fused pipeline cost

```
Single stage:  N_scan × N_z × N_relax × N_atoms pair evals  (no grid, no global write)
```

Same numbers: 2500 × 60 × 50 × 64 = **480M pair evals**, all in registers/local memory.

So brute-force does ~7.5× more pair evaluations. **But:**

1. **No 16 MB grid allocation + write.** The grid build is memory-bound (writing 16 MB to global), while pair evals are compute-bound (`exp`, `sqrt` — well-suited to GPU).
2. **No grid discretization error.** The projection approach interpolates the grid during relaxation (`interpFE` → trilinear/B-spline). Brute-force evaluates the exact potential at the probe position.
3. **No kernel launch overhead** for the grid build (one fewer kernel, one fewer `queue.finish()`).
4. **For 32 atoms with fast convergence (20 steps):** 2500 × 60 × 20 × 32 = **96M** vs 64M grid build. Nearly break-even, and you save the entire grid memory + bandwidth.
5. **Differentiability** — the killer feature. The grid is a non-differentiable intermediate. Brute-force gives you ∂E/∂(atom params) directly, enabling force-field fitting against AFM images.

The crossover point is roughly **N_atoms ≲ 64 with N_relax ≲ 40**. Below that, brute-force wins or breaks even. Above, the grid amortizes.

## Proposed Kernel Design

### Core idea: fuse the atom loop into the relaxation loop

Replace `interpFE(pos, ..., imgIn)` (texture read from precomputed grid) with `evalBruteMorseC(pos, LATOMS, LCMS, nAtoms, Qs, QZs)` (direct atom sum from local memory).

### Key optimization: load atoms into local memory ONCE

The critical insight: **atoms don't change during relaxation**. In the projection kernel, atoms are loaded into local memory per grid point. In the brute-force relaxation, atoms are loaded **once per workgroup** and reused across all z-slices × relaxation steps.

For 64 atoms: `2 × 64 × float4 = 2 KB` of local memory — trivial. Loaded once, used ~60×50 = 3000 times. This is the ideal local-memory reuse pattern from the gpu-optimize skill.

### Two variants based on molecule size

**Variant A: `nAtoms ≤ WG_SIZE` (small molecule, fast path)**

All atoms fit in one local-memory tile. Load once before the relaxation loop, no barriers during relaxation:

```c
// Pseudocode — relaxBruteForce_MorseC_small
__attribute__((reqd_work_group_size(WG,1,1)))
__kernel void relaxBruteForce_MorseC_small(
    const int nAtoms,
    __global const float4* atoms,   // (x,y,z,q)
    __global const float4* cMs,     // (R0,E0,alpha,_)
    __global const float4* points,  // scan tip positions
    __global float4* FEs,           // output (Fx,Fy,Fz,E)
    __global float4* disps,         // output displacement
    float4 tipA, float4 tipB, float4 tipC,
    float4 stiffness, float4 dpos0,
    float4 relax_params, float4 surfFF,
    float4 Qs, float4 QZs,
    int nz
){
    __local float4 LATOMS[WG_MAX];   // e.g. 128
    __local float4 LCMS  [WG_MAX];
    const int iG = get_global_id(0);
    const int iL = get_local_id(0);
    const int nL = get_local_size(0);

    // --- Load ALL atoms into local memory ONCE (collaborative) ---
    for(int i=iL; i<nAtoms; i+=nL){
        LATOMS[i] = atoms[i];
        LCMS  [i] = cMs  [i];
    }
    Qs *= COULOMB_CONST;
    barrier(CLK_LOCAL_MEM_FENCE);
    // --- Atoms stay in local memory for the ENTIRE relaxation ---

    float4 dpos0_ = dpos0;
    dpos0_.xyz = rotMatT(dpos0_.xyz, tipA.xyz, tipB.xyz, tipC.xyz);
    float3 dTip = tipC.xyz * tipC.w;
    float3 tipPos = points[iG].xyz;
    float3 pos = tipPos + dpos0_.xyz;
    float dt = relax_params.x, damp = relax_params.y;
    float dtmax = dt, dtmin = dtmax*0.1f, damp0 = damp;

    for(int iz=0; iz<nz; iz++){
        float4 fe; float3 v = 0.0f;
        for(int i=0; i<N_RELAX_STEP_MAX; i++){
            // --- BRUTE FORCE: sum over all atoms from local memory ---
            fe = (float4)(0,0,0,0);
            for(int j=0; j<nAtoms; j++){
                float4 xyzq = LATOMS[j];
                float3 dp = pos - xyzq.xyz;
                fe += getMorse(dp, LCMS[j].xyz);
                fe += getCoulombAFM(xyzq, pos+(float3)(0,0,QZs.x)) * Qs.x;
                fe += getCoulombAFM(xyzq, pos+(float3)(0,0,QZs.y)) * Qs.y;
                fe += getCoulombAFM(xyzq, pos+(float3)(0,0,QZs.z)) * Qs.z;
                fe += getCoulombAFM(xyzq, pos+(float3)(0,0,QZs.w)) * Qs.w;
            }
            // --- tip spring + surfFF (same as relaxStrokesTilted) ---
            float3 f = fe.xyz;
            float3 dpos_ = rotMat(pos - tipPos, tipA.xyz, tipB.xyz, tipC.xyz);
            f += rotMatT(tipForce(dpos_, stiffness, dpos0), tipA.xyz, tipB.xyz, tipC.xyz);
            f += tipC.xyz * surfFF.x;
            v = update_FIRE(f, v, &dt, &damp, dtmin, dtmax, damp0);
            v += f * dt;
            pos += v * dt;
            if(dot(f,f) < F2CONV) break;
        }
        // final fe at relaxed pos
        fe = (float4)(0,0,0,0);
        for(int j=0; j<nAtoms; j++){ /* same atom sum */ }
        float4 fe_; fe_.xyz = rotMat(fe.xyz, tipA.xyz, tipB.xyz, tipC.xyz); fe_.w = fe.w;
        FEs  [iG*nz + iz] = fe_;
        disps[iG*nz + iz] = (float4)(pos - (tipPos + dpos0_.xyz), 0);
        tipPos += dTip.xyz;
        pos += dTip.xyz;
    }
}
```

**No barriers inside the relaxation loop.** The atom loop is pure local-memory reads — every thread reads the same `LATOMS[j]` (broadcast, no bank conflicts since all threads read the same index).

**Variant B: `nAtoms > WG_SIZE` (tiled path)**

Tile atoms in chunks of `nL` with barriers, same pattern as `cs_brute_afm_morse_c_points` but called inside the relaxation loop. This adds `ceil(nAtoms/nL)` barriers per relaxation step. For 128 atoms with WG=32: 4 barriers/step × 50 steps × 60 z = 12000 barriers per scan point. Still likely faster than grid build for 128 atoms, but the advantage shrinks.

### Workgroup size selection

| nAtoms | Recommended WG | Rationale |
|--------|---------------|-----------|
| ≤ 32 | 128-256 | Atoms fit in 1 tile; large WG maximizes occupancy. Local mem: 2×32×16 = 1 KB. |
| 33-64 | 128 | Atoms fit in 1 tile if `WG_MAX ≥ 64`. Local mem: 2 KB. |
| 65-128 | 128 | Load all atoms collaboratively (loop `i+=nL`), 1 barrier. Local mem: 4 KB. |
| 129-256 | 64-128 | Tiled: 2-4 tiles per force eval. Barriers per step. |

NVIDIA SM has 48 KB local memory, 2048 threads max. WG=128 → 16 workgroups/SM, 1 KB local each → trivial. **Register pressure is the real constraint**: the relaxation loop uses ~12 live floats (pos, v, dt, damp, fe) + atom-loop temporaries (~8 floats). ~20 registers/thread → 2048/20 = 102 threads/SM occupancy-limited. WG=128 with 16 registers spill is fine; WG=256 may spill. **I'd start with WG=128.**

### Differentiability design

For force-field fitting, you need ∂E_total/∂p where p = {R0_i, E0_i, alpha_i, Q_i} per atom. Two approaches:

**1. Fused analytic gradient (recommended, zero overhead)**

The Morse energy derivatives are cheap and share the intermediate `e = exp(alpha*(r-R0))`:

```
E_morse = E0 * e * (e - 2)
∂E/∂R0   = 2*alpha*E0*e*(e - 1)     = -fr_morse * r / (2*alpha)  [reuse fr]
∂E/∂E0   = e*(e - 2)                 = E_morse / E0
∂E/∂alpha = 2*E0*e*(e-1)*(r-R0)     = -fr_morse * r * (r-R0) / (2*alpha)
∂E/∂Q    = COULOMB_CONST / sqrt(r²+R2damp)   [Coulomb, reuse ir_]
```

Add a gradient accumulation loop alongside the force loop, writing `dE_dp[nAtoms*4]` to a per-thread output buffer. After the scan, reduce on host (or a separate reduction kernel). This follows the "fuse secondary checks into existing kernels" pattern — the `exp` and `sqrt` are already computed for the force.

**2. External AD (JAX/PyTorch wrapping)**

Write the pair potential in JAX, vmap over atoms, and use `jax.grad`. Slower but flexible. Better for prototyping the loss function; the fused kernel is for production fitting.

            // --- tip spring + surfFF (same as relaxStrokesTilted) ---
            float3 f = fe.xyz;
            float3 dpos_ = rotMat(pos - tipPos, tipA.xyz, tipB.xyz, tipC.xyz);
            f += rotMatT(tipForce(dpos_, stiffness, dpos0), tipA.xyz, tipB.xyz, tipC.xyz);
            f += tipC.xyz * surfFF.x;
            v = update_FIRE(f, v, &dt, &damp, dtmin, dtmax, damp0);
            v += f * dt;
            pos += v * dt;
            if(dot(f,f) < F2CONV) break;
        }
        // final fe at relaxed pos
        fe = (float4)(0,0,0,0);
        for(int j=0; j<nAtoms; j++){ /* same atom sum */ }
        float4 fe_; fe_.xyz = rotMat(fe.xyz, tipA.xyz, tipB.xyz, tipC.xyz); fe_.w = fe.w;
        FEs  [iG*nz + iz] = fe_;
        disps[iG*nz + iz] = (float4)(pos - (tipPos + dpos0_.xyz), 0);
        tipPos += dTip.xyz;
        pos += dTip.xyz;
    }
}
```

**No barriers inside the relaxation loop.** The atom loop is pure local-memory reads — every thread reads the same `LATOMS[j]` (broadcast, no bank conflicts since all threads read the same index).

**Variant B: `nAtoms > WG_SIZE` (tiled path)**

Tile atoms in chunks of `nL` with barriers, same pattern as `cs_brute_afm_morse_c_points` but called inside the relaxation loop. This adds `ceil(nAtoms/nL)` barriers per relaxation step. For 128 atoms with WG=32: 4 barriers/step × 50 steps × 60 z = 12000 barriers per scan point. Still likely faster than grid build for 128 atoms, but the advantage shrinks.

### Workgroup size selection

| nAtoms | Recommended WG | Rationale |
|--------|---------------|-----------|
| ≤ 32 | 128-256 | Atoms fit in 1 tile; large WG maximizes occupancy. Local mem: 2×32×16 = 1 KB. |
| 33-64 | 128 | Atoms fit in 1 tile if `WG_MAX ≥ 64`. Local mem: 2 KB. |
| 65-128 | 128 | Load all atoms collaboratively (loop `i+=nL`), 1 barrier. Local mem: 4 KB. |
| 129-256 | 64-128 | Tiled: 2-4 tiles per force eval. Barriers per step. |

NVIDIA SM has 48 KB local memory, 2048 threads max. WG=128 → 16 workgroups/SM, 1 KB local each → trivial. **Register pressure is the real constraint**: the relaxation loop uses ~12 live floats (pos, v, dt, damp, fe) + atom-loop temporaries (~8 floats). ~20 registers/thread → 2048/20 = 102 threads/SM occupancy-limited. WG=128 with 16 registers spill is fine; WG=256 may spill. **I'd start with WG=128.**

### Differentiability design

For force-field fitting, you need ∂E_total/∂p where p = {R0_i, E0_i, alpha_i, Q_i} per atom. Two approaches:

**1. Fused analytic gradient (recommended, zero overhead)**

The Morse energy derivatives are cheap and share the intermediate `e = exp(alpha*(r-R0))`:

```
E_morse = E0 * e * (e - 2)
∂E/∂R0   = 2*alpha*E0*e*(e - 1)     = -fr_morse * r / (2*alpha)  [reuse fr]
∂E/∂E0   = e*(e - 2)                 = E_morse / E0
∂E/∂alpha = 2*E0*e*(e-1)*(r-R0)     = -fr_morse * r * (r-R0) / (2*alpha)
∂E/∂Q    = COULOMB_CONST / sqrt(r²+R2damp)   [Coulomb, reuse ir_]
```

Add a gradient accumulation loop alongside the force loop, writing `dE_dp[nAtoms*4]` to a per-thread output buffer. After the scan, reduce on host (or a separate reduction kernel). This follows the "fuse secondary checks into existing kernels" pattern — the `exp` and `sqrt` are already computed for the force.

**2. External AD (JAX/PyTorch wrapping)**

Write the pair potential in JAX, vmap over atoms, and use `jax.grad`. Slower but flexible. Better for prototyping the loss function; the fused kernel is for production fitting.
